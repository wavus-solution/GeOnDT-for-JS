# AI 작업자를 위한 GeOnDT 개발 지침

[아카이브 소개](../README.md) · [공식 자료 탐색 방법](reference-guide.md)

이 문서는 **사용자의 개발 요청을 수행하는 AI 작업자**를 위한 지침입니다. GeOnDT의 기본 사용법을 배우려는 분은 [시작하기와 기능 안내](../doc/home/index.html), [공식 예제](../doc/tutorial-official/index.html)를 먼저 확인하십시오.

이 지침은 사용자 요구를 GeOnDT의 기능과 연결하여 고객 서비스에 구현하는 공통 접근법입니다. 요구를 이해하고, 모르는 부분을 조사하고, 기능을 조합하고, 실제 결과를 확인하는 과정을 안내합니다. 탐색 중 제약이 확인되면 설계를 바꾸고 다시 확인합니다. 작은 수정은 관련 부분만 적용하고, 여러 기능이 얽힌 작업은 연결 관계까지 살펴보십시오.

## 1. 사용자가 얻으려는 결과부터 정하기

먼저 사용자가 어떤 상황에서 무엇을 입력·조작하고, 어떤 결과를 얻어 이후에 어떻게 활용하려는지 파악합니다. 기능 이름만으로 구현 범위를 결정하지 말고 결과의 의미, 필요한 정확도와 응답성, 저장·공유 여부 등 성공 조건을 확인합니다.

기존 고객 프로젝트에서 다음 정보를 먼저 조사합니다. 이미 코드와 설정에 있는 내용을 사용자에게 다시 묻지 않습니다.

- 사용하는 GeOnDT 배포본, 지도 인스턴스, 프레임워크와 언어, 기존 화면·상태 관리 방식.
- 입력 데이터의 출처·형식·좌표계·단위, 접속 조건, 데이터가 준비되는 시점.
- 기존 기능과 함께 동작해야 하는 범위, 외부 서비스와의 연결, 실행·배포 환경.

결과나 구현 가능성을 바꾸는 조건이 빠져 있으면 해당 조건만 확인합니다. 확인된 사실, 아직 확인할 조건, 우선 적용할 가정을 구분하고, 미정인 부분과 독립적으로 진행할 수 있는 부분을 나눕니다.

## 2. 복합 요구를 데이터와 동작의 연결로 풀기

사용자 조작부터 최종 결과 활용까지 흐름을 그려 보고, 각 처리의 입력·출력과 선행 조건을 적습니다. 여러 단계가 병렬로 진행되거나 반복·분기할 수 있으며, 각 단계가 GeOnDT 클래스 하나와 대응할 필요는 없습니다.

예를 들어 사용자가 데이터를 불러와 지도에서 편집하고, 여러 결과를 비교한 뒤 저장하는 서비스를 요청했다면 불러오기·편집·계산·비교·저장을 함께 살펴봅니다. 편집 결과가 바뀌면 어떤 계산이 무효가 되는지, 저장할 때 어떤 입력과 결과를 한 묶음으로 보존해야 하는지가 연결 지점입니다. 이 흐름에서 요구되는 지도 기능과 데이터 처리를 조사합니다.

GeOnDT에 맡길 지도·공간 처리와 고객 앱이 맡을 화면 상태·업무 규칙·저장·외부 통신의 역할을 정합니다. 실제 제공 범위는 [공식 자료 탐색 방법](reference-guide.md)으로 확인하십시오. 서비스 요구 전체를 처리하는 단일 API나 똑같은 공식 예제가 있어야 구현할 수 있는 것은 아닙니다.

각 연결에서 다음 질문으로 설계의 빈틈을 찾습니다.

| 연결 지점 | 확인할 내용 |
|---|---|
| 데이터 전달 | 앞 단계의 출력이 다음 단계의 입력 형식·좌표계·높이 기준·단위·대상 종류와 맞는가? 변환이 필요한가? |
| 실행 시점 | 무엇이 준비되어야 시작할 수 있고, 언제 완료되었다고 판단하는가? 지도 준비와 개별 데이터 준비는 같은가? |
| 상태 변경 | 입력이나 대상이 바뀌면 어떤 결과가 오래된 것이 되는가? 동시 요청과 반복 조작은 어떻게 구분하는가? |
| 공유 자원 | 지도·레이어·선택 상태·마우스 입력을 누가 관리하는가? 함께 실행되는 기능이 서로 간섭하는가? |
| 종료와 복구 | 실패·취소·재시도·화면 이동 때 어떤 이벤트·객체·결과를 유지하거나 정리해야 하는가? |

각 단계가 따로 성공해도 서로의 데이터와 실행 조건이 맞아야 전체 요구가 작동합니다. 필요한 연결부터 확인하고 작업의 규모에 맞게 메모나 설계에 남깁니다.

## 3. 불확실한 연결부터 확인하기

설계를 좌우하는 질문부터 조사합니다. 특정 데이터가 지원되는지, 필요한 결과를 얻을 수 있는지, 입력 시점과 처리 시점을 제어할 수 있는지처럼 잘못 가정하면 뒤 작업을 다시 해야 하는 부분을 우선합니다.

공식 자료에서 후보 API를 찾으면 입력·출력·제약과 사용 근거를 확인합니다. 다음 정도의 메모면 이후 구현에서 같은 탐색을 반복하지 않을 수 있습니다. 별도 문서 양식을 만들 필요는 없습니다.

- 확인할 질문과 채택한 API·사용 경로.
- 근거가 된 문서·예제·선언의 위치와 고객 배포본에서 확인한 결과.
- 남은 조건 또는 제약, 그 조건을 확인할 다음 방법.

문서만으로 핵심 연결을 판단하기 어렵다면 실제 배포본과 대표 데이터로 작은 실행을 만들어 확인합니다. 가장 불확실한 연결을 포함하여 입력부터 의미 있는 출력까지 통과시키고, 확인된 흐름에 나머지 기능을 붙입니다. 개별 API 호출 성공만으로 복합 요구 전체가 가능하다고 판단하지 않습니다.

공개 API 조합으로 구현 가능한 부분, 고객 앱이나 외부 서비스가 담당할 부분, 현재 자료로 확인할 수 없는 부분을 구분합니다. 필수 조건을 만족하는 경로가 확인되지 않으면 근거와 영향 범위를 알려 해결 방향을 정합니다. 존재하지 않는 API를 가정하거나 사용자 요구를 조용히 줄이지 않습니다.

## 4. 고객 서비스의 구조에 맞춰 구현하기

기존 지도 인스턴스와 고객 앱의 컴포넌트·상태 관리 구조에 연결합니다. 예제에서 필요한 생성·호출·이벤트 흐름을 가져오되, 예제 페이지의 전역 변수·UI·테스트 주소까지 그대로 이식하지 않습니다. 외부 데이터와 고객 설정은 실제 환경에 연결합니다.

비동기 처리의 시작·완료·실패를 구분하고, 입력이 바뀌거나 재실행되었을 때 이전 요청의 결과가 최신 화면을 덮지 않도록 합니다. 취소와 정리는 해당 API가 지원하는 방법으로 처리합니다. API에 취소 기능이 없다면 결과를 무시하는 처리와 실제 작업 중단이 다르다는 점을 반영합니다.

여러 기능이 지도와 입력 장치를 공유하면 활성 입력 모드와 이벤트 등록·해제 책임을 정합니다. 화면을 다시 열거나 기능을 반복 실행해도 이벤트와 객체가 쌓이지 않는지 확인합니다. 객체 제거와 자원 해제의 의미도 해당 API에서 확인합니다.

자료에서 검증한 사용 조건을 코드에 반영하고, 연결을 바꿀 때는 영향을 받는 흐름을 다시 확인합니다. 공개 구현이 없는 기능도 문서화된 API로 사용하며, 비공개 구현을 추측하여 서비스 코드에 복제하지 않습니다.

## 5. 실행 환경과 배포본 연결하기

서비스에서 사용하는 제품은 [dist](../dist/)입니다. `src`의 JS와 d.ts는 읽기용 참조 자료입니다. 고객 앱의 실행 import와 타입 연결에는 해당 서비스에 배치한 dist를 사용합니다.

- 일반 스크립트는 `GeOnDT.min.js`, ES 모듈은 `GeOnDT.modules.js`를 사용합니다. 타입 전용 이름은 `import type`으로 구분합니다. 이름이 선언에 있다는 것과 생성 가능한 런타임 객체라는 것은 다르므로 값 export와 사용법을 확인합니다.
- 모듈 import 완료와 제품 초기화 완료를 구분합니다. 공식 사용 흐름의 `GeOnDT.ready`에서 지도를 만들고 `GeOnDT.fail`로 초기화 실패를 처리합니다. 개별 레이어나 데이터 준비 시점은 별도로 확인합니다.
- `GeOnDT.config.js`와 worker·resource·wasm 등 실행에 필요한 dist 파일을 함께 배치합니다. `baseUrl`은 해당 리소스 폴더들이 있는 배포 디렉터리를 가리킵니다. 빈 문자열이면 경로 자동 탐색을 사용하며 설정 파일이 없으면 초기화가 실패합니다.
- 고객 앱에서 재번들링한다면 설정을 수정한 뒤 앱을 빌드하고, 정적 리소스가 실제 서비스 경로에서 로드되는지 확인합니다.
- SSR을 사용하는 서비스에서는 브라우저 실행 경로에서 제품을 가져오고 초기화합니다. 지도 렌더링은 브라우저에서 수행합니다.

아카이브와 고객 제품의 버전이 다르면 고객 배포본에서 API와 동작을 확인합니다. 라이선스·서버 주소·데이터 접속 조건은 고객 환경을 따릅니다. 자료의 차이를 판단하는 방법은 [공식 자료 탐색 방법](reference-guide.md)에 정리되어 있습니다.

## 6. 사용자 요구 전체로 검증하기

처음 정한 성공 조건과 연결 관계를 기준으로 검증합니다. 다음 항목 중 작업에 영향을 주는 것을 선택하고, 숫자 기준이나 대표 데이터가 필요하면 검증 전에 정합니다.

- 실제 사용하는 배포본으로 TypeScript 타입 검사와 고객 앱 빌드가 통과하는지 확인합니다.
- 브라우저에서 초기화·리소스 로드·데이터 준비부터 사용자 조작과 최종 결과 활용까지 이어지는 흐름을 확인합니다.
- 반복 실행, 입력 변경, 취소, 실패 후 재시도, 화면 이동과 여러 기능의 동시 사용에서 상태와 자원이 올바르게 관리되는지 확인합니다.
- 공간 결과는 좌표계·높이 기준·단위와 기준 데이터의 기대값을 대조합니다. 숫자나 그림이 표시된 것만으로 의미와 정확성이 검증된 것은 아닙니다.
- 처리량이나 응답성이 요구에 포함되면 고객 환경에 가까운 데이터 규모와 장치에서 측정합니다. 작은 예제의 성공을 대규모 데이터의 성능 근거로 삼지 않습니다.

완료 보고에는 구현한 요구, 사용한 API와 참고 근거, 필요한 고객 설정, 실행한 검증과 미검증 범위를 적습니다. 타입 검사 성공, 브라우저 동작, 결과 정확도, 성능 확인은 각각의 증거로 구분합니다. 확인되지 않은 부분은 영향과 다음 확인 방법을 함께 남깁니다.
