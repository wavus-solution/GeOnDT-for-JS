# AI 작업자를 위한 공식 자료 탐색 방법

[아카이브 소개](../README.md) · [GeOnDT 개발 지침](development-guide.md)

이 문서는 **GeOnDT를 사용하는 코드를 작성할 AI 작업자**가 필요한 자료를 찾고 판단하는 방법을 설명합니다. 제품의 기능과 사용법을 바로 보고 싶은 분은 [시작하기와 기능 안내](../doc/home/index.html), [공식 예제](../doc/tutorial-official/index.html)로 이동하십시오.

GeOnDT의 기능은 기능 안내·API 문서·공식 예제에서 발견하고, 타입 선언과 동작 명세·공개 소스로 사용 조건을 확인합니다. 이 문서는 작업마다 필요한 정보를 스스로 찾아 판단하는 방법을 안내합니다. 모든 자료를 정해진 순서로 읽을 필요는 없습니다. 지금 해결해야 할 질문에 맞는 자료에서 시작하여 필요한 연결만 따라가십시오.

### 시작 예제에서 바로 확인할 코드

제품을 처음 연결하거나 초기화 흐름을 확인할 때는 아래 파일부터 읽습니다. JavaScript와 TypeScript 예제는 같은 지도 동작을 제공합니다.

| 확인할 내용 | JavaScript / ES 모듈 | TypeScript / Vite |
|---|---|---|
| 라이선스 로드, 제품 import, 준비 대기, 지도 생성·해제, 오류 표시 | [src/main.js](../starters/esm/src/main.js) | [src/main.ts](../starters/typescript-vite/src/main.ts) |
| 초기 위치, 배경지도, 라이선스·제품 URL | [src/settings.js](../starters/esm/src/settings.js) | [src/settings.ts](../starters/typescript-vite/src/settings.ts) |
| 실행 명령·개발 도구 | [package.json](../starters/esm/package.json) | [package.json](../starters/typescript-vite/package.json) |
| 앱 빌드와 정적 제품 파일 복사 | 앱 빌드 없음 | [vite.config.ts](../starters/typescript-vite/vite.config.ts) |

[실행 안내](getting-started.md)의 준비 명령은 제품과 기본 `localhost` 라이선스를 실행용 `static`에 복사합니다. 이 폴더와 TypeScript 예제의 `node_modules`·`build`는 로컬 명령 실행 후 생성되므로 GitHub에 없다고 누락으로 판단하지 않습니다. TypeScript의 실제 선언 연결은 `src/main.ts`의 import 경로와 준비된 제품의 `GeOnDT.modules.d.ts`에서 확인합니다.

시작 예제는 제품 연결과 기본 지도 동작을 보여 줍니다. 사용자 요구에 필요한 기능·데이터·이벤트는 다음 탐색 방법으로 찾아 연결하고, 사용 조건과 결과를 검증합니다.

## 2. 사용자 표현에서 GeOnDT 용어와 API 이름 찾기

사용자 요구를 대상 데이터, 원하는 조작, 필요한 결과, 제약으로 풀어 검색어를 만듭니다. 긴 요청 문장 전체보다 각 의미를 나누어 찾고, 관련된 한국어 표현과 영문 용어도 확인합니다. 검색어가 제품에서 사용하는 이름과 같을 필요는 없습니다.

처음에는 `doc/home`의 설명과 `doc/tutorial-official`의 목록·예제 본문에서 가까운 개념을 찾습니다. 발견한 용어로 검색 범위를 좁히고, 예제의 실제 생성·호출 부분에서 API 이름과 접근 경로를 얻습니다. 클래스 이름뿐 아니라 생성 옵션, 이벤트 이름, 반환 객체의 타입도 다음 탐색의 단서가 됩니다.

HTML 목록이 다른 페이지로 이동하거나 별도 목록·스크립트를 읽는다면 실제 연결 대상까지 확인합니다. 예제 코드도 HTML 안에 있거나 연결된 JS·코드 파일에 있을 수 있습니다. 화면 제목과 미리보기만 보고 동작을 판단하지 않습니다. GitHub에서 HTML 소스만 보여도 본문과 연결된 코드를 읽어 탐색할 수 있습니다.

API 이름을 알고 있다면 문서나 색인으로 바로 이동합니다. 한 기능의 입력 타입·반환 타입·상위 클래스·관련 이벤트를 따라가면 함께 사용할 기능을 발견할 수 있습니다. `GeOnDT`의 static 멤버와 그룹은 공개 접근 경로를 살펴보는 단서이며, 속성 이름·타입 이름·import 이름이 항상 같은지는 실제 선언과 예제로 확인합니다.

로컬 파일 검색이나 GitHub 검색 등 사용 가능한 도구를 이용하십시오. 처음부터 압축된 dist나 모든 선언을 통째로 읽기보다 설명·예제에서 후보 이름을 찾고 관련 파일로 좁힙니다. 완전히 일치하는 예제가 없으면 필요한 역할을 각각 보여 주는 예제를 찾아 연결 조건을 확인합니다.

## 3. 색인에서 선언과 동작 근거로 이동하기

`api-index.json`은 export 이름을 경로에 연결하는 JSON 배열입니다. 항목의 필드는 다음과 같습니다.

| 필드 | 읽는 방법 |
|---|---|
| `name` | 배포본에서 export하는 이름을 검색합니다. |
| `kind` | `value`는 값 export, `type`은 타입 export입니다. 값 export라고 해서 모두 생성자는 아닙니다. |
| `declaration` | 아카이브 루트를 기준으로 한 분리 d.ts 경로입니다. 해당 이름과 관련된 입력·출력 타입을 읽습니다. |
| `source`, `spec` | 제공되는 경우 공개 JS와 명세의 경로입니다. 없으면 공개된 파일이 있다고 가정하지 않습니다. |

이 색인은 기능 설명 전체나 개별 메서드·이벤트를 나열한 목록이 아닙니다. 찾는 메서드 이름이 없으면 해당 클래스의 API 문서와 선언을 확인하고 상속한 멤버도 따라갑니다. 색인에서 검색되지 않는다는 이유만으로 제품에 기능이 없다고 결론 내리지 않습니다.

분리 d.ts에서는 인수의 관련 타입과 상속 관계를 확인합니다. 참조하는 다른 선언이 필요하면 그 파일까지 읽되, 현재 질문과 관계없는 타입 전체를 펼칠 필요는 없습니다. `src`에 있는 선언의 export와 실제 배포 모듈에서 import 가능한 이름은 구분하고, 최종 연결은 `dist/GeOnDT.modules.d.ts`와 고객 배포본을 확인합니다.

spec과 공개 JS는 타입만으로 알기 어려운 동작을 보완합니다. spec은 공개 참조용 발췌본이며 일부는 관찰 초안입니다. 공개 JS가 없는 기능도 API·예제·선언으로 사용할 수 있습니다. 선언이나 소스에 보이는 내부 멤버를 곧바로 서비스용 API로 취급하지 말고 공식 사용 경로를 확인합니다.

## 4. 후보가 요구에 맞는지 판단하기

비슷한 이름을 찾는 것은 후보를 발견한 단계입니다. 실제 선택은 다음 조건을 비교한 뒤에 합니다.

- 고객 데이터의 종류·형식과 좌표계·높이 기준·단위를 지원하는가?
- 필요한 입력 방식과 실행 시점을 제어할 수 있는가? 자동으로 진행되는 부분은 무엇인가?
- 필요한 결과의 의미·형식·정확도 조건과 일치하는가? 다음 단계에 전달할 수 있는가?
- 준비·완료·실패를 확인할 수 있는가? 반복 실행과 종료 시 처리 방법은 무엇인가?
- 고객 배포본과 실행 환경에서 사용할 수 있으며 필요한 데이터·서비스에 접근할 수 있는가?

공식 예제는 그 예제의 조건에서 API를 조합한 근거입니다. 예제에서 생략한 실패 처리나 특정 테스트 데이터의 특성까지 모든 서비스의 보장으로 확대하지 않습니다. 예제와 고객 요구의 차이를 정리하고 차이가 있는 연결부터 확인합니다.

필요한 사용 경로, 입출력 조건, 실행 시점과 정리 방법이 확인되면 구현·검증으로 이동합니다. 자료를 모두 읽기 위해 탐색을 계속할 필요는 없습니다. 실행 중 새로운 조건이 드러나면 그 질문에 맞춰 다시 탐색합니다.

## 5. 자료가 부족하거나 서로 다를 때

검색 결과가 없으면 표현을 바꾸고 주변 개념, 상위 클래스, 입력·출력 타입과 가까운 예제로 범위를 넓힙니다. 그래도 근거를 찾지 못했다면 “지원하지 않음”과 “공개 자료에서 확인하지 못함”을 구분합니다. 다른 엔진의 메서드 이름이나 비슷한 옵션을 GeOnDT API로 추정하지 않습니다.

자료가 충돌하면 고객 제품과 아카이브의 배포 시점을 먼저 확인하고, 어떤 파일의 어떤 설명이 다른지 기록합니다. 타입·export는 고객 배포본의 선언과 실제 JS를, 동작은 해당 환경의 최소 재현을 대조합니다. 타입 검사를 강제로 무시하거나 출처 하나만 골라 차이를 감추지 않습니다. 현재 버전에서 확인된 사용 범위 안에서 진행하고, 결과를 바꾸는 불확실성은 해결한 뒤 해당 구현을 확정합니다.

검색한 경로와 확인한 사실, 남은 질문을 간결하게 남기면 다음 구현이나 작업 인계에서 재사용할 수 있습니다. 아카이브의 일반 지침에 기능별 목록을 복제할 필요는 없습니다. 기능과 API의 설명은 공식 자료에서 찾아 연결하고, 이 지침은 그 자료를 발견하고 판단하는 방법으로 사용합니다.
